Findings

    How serving is measured

    Runs right after the engine is ready, inside the same sandbox against localhost, so network latency to the client is excluded (serving_load() in bench_runner.py).

    • Workload: ~800-word prompt (~1,000 tokens), prefixed with the request number so no two requests share a cached prefix; exactly 256 output tokens (greedy, ignore_eos); streaming /generate.
    • Concurrency 32: 128 requests, 32 in flight at a time: throughput-bound.
    • Concurrency 1: 16 requests, one after another: latency-bound, where CUDA graphs matter most.
    • TTFT: request sent → first streamed chunk.
    • ITL (per-token latency): per request, (total − TTFT) ÷ (tokens − 1); p50/p99 across requests.
    • Throughput: all output tokens ÷ wall time of the whole batch.
    • Correctness: greedy output of 3 fixed prompts, hashed, compared with the baseline.
    • Limits: ITL is a per-request average (stalls inside a request are smoothed); a simple Python client, not SGLang's bench_serving, so compare approaches within this project rather than with published numbers; measures serving just after startup, not long steady state.

    What the trials say so far

      Architecture: artifact catalog, scheduler, workers

      Startup is treated as assembling artifacts. The scheduler reads the catalog, prepares on CPU what it can, claims GPUs late, and learns its estimates from every launch. Live numbers below come from the catalog in Postgres and results/scheduler/.
